# CoffeeVerifier — ESP32-CAM: верификация налива кофе по триггеру

Камера смотрит сверху в стаканчик под носиком кофемашины. Терминал «оплатил
кофе» дёргает HTTP-триггер `/verify` (эмуляция платёжного события) — камера
открывает окно верификации и решает: **действительно ли машина налила напиток**,
по изменению ROI относительно baseline-кадра, снятого в момент триггера. Это
ловит ситуацию «деньги списали, а кофе не приготовился».

```
[терминал: оплачено, drink=latte]
   → GET /verify?drink=latte           (эмуляция триггера)
   → baseline (пустой стакан) → окно ~30с → следим за изменением от baseline
   → вердикт: ok / not_dispensed / wrong_drink
   → NDJSON по TCP → слушатель на ПК (+ хранится как last_verdict)
```

Это самостоятельная прошивка в `CoffeeVerifier/`, выросшая из соседнего
LED-детектора (то же ядро: камера RGB565/QQVGA, ROI, фикс-экспозиция, TCP-репортер,
рантайм-конфиг в NVS). Разница — вместо непрерывной классификации тут **триггерное
окно** и решение по **дельте от baseline**.

## Две оси решения (важно)

| Ось | Кто решает | Почему так |
|---|---|---|
| **налито / не налито** (деньги) | дельта ROI от baseline-кадра, **без ML** | большое изменение «пусто → жидкость», устойчиво к свету; работает в день один |
| **с молоком / без** (соответствие заказу) | порог яркости (этап 1) → CNN (этап 2) | цветовая задача; ошибка тут не влияет на денежный вердикт |

Вердикт — это «**содержимое изменилось за окно**», а не «в конце стакан полный»:
забытый полный стакан в момент триггера НЕ считается наливом. Окно **всегда**
завершается — таймаут даёт `not_dispensed`, верификатор не зависает (проверка
дедлайна по wall-clock срабатывает даже при стопоре кадров камеры).

Денежная и молочная оси разведены по времени: `dispensed` фиксируется по
**первому** устойчивому изменению (рано и надёжно), а молоко читается уже с
**устоявшегося** кадра — когда содержимое перестало меняться (плато ~1с) или по
концу окна. Поэтому латте, который сначала льёт тёмный эспрессо, а молоко
секундами позже, классифицируется по финалу, а не по тёмной ранней фазе.

## Прошивка

Тулчейн тот же, что у родительского проекта (`esp32:esp32@3.3.8`, `WiFiManager`).
**TensorFlow/Chirale для MVP не нужны** — CNN не используется.

```bash
arduino-cli compile --fqbn esp32:esp32:esp32cam coffee/CoffeeVerifier
arduino-cli upload  --fqbn esp32:esp32:esp32cam --port /dev/cu.usbserial-XXX coffee/CoffeeVerifier
```

Первый запуск — как в корневом README: сеть `ESP32-CAM-Setup` (captive portal) →
выбрать WiFi. Камера анонсится по mDNS как **`http://coffeecam.local/`**.

## Прицеливание и тюнинг (workflow отладки)

Всё настраивается в рантайме через HTTP и сохраняется в NVS — **без перепрошивки**.

1. **Навести ROI на горло стакана.** Открой `http://coffeecam.local/capture?roi=1`
   — кадр с зелёной рамкой ROI. Двигай рамку, пока она не ляжет на поверхность
   внутри стакана:
   ```
   curl "http://coffeecam.local/cupcfg?roi_x=50&roi_y=30&roi_w=60&roi_h=60"
   ```
2. **Зафиксировать экспозицию** (иначе авто-AEC «вытянет» тёмный кофе обратно к
   яркости пустого стакана и убьёт дельту):
   ```
   curl "http://coffeecam.local/cupcfg?fixexp=1&aec_value=600&agc_gain=0"
   ```
3. **Смотреть живые метрики** во время теста — главный инструмент отладки:
   ```
   watch -n0.3 'curl -s http://coffeecam.local/metrics'
   ```
   Поля `live.{r,g,b,y}` — текущее среднее по ROI. Поставь пустой стакан, запиши
   `y`; налей кофе — увидишь, на сколько `y`/каналы уехали. Это и есть твоя дельта.
4. **Подобрать пороги** по наблюдениям:
   - `fill_delta` — насколько должно измениться среднее по каналам, чтобы счесть
     «налито» (дефолт 25). Ставь чуть ниже реально наблюдаемого скачка.
   - `settle` — сколько кадров подряд держится изменение, чтобы подтвердить
     (дефолт 6 ≈ 0.3с при 20 Гц) — отсекает руку/всплеск.
   - `milk_luma` — порог яркости «молочный/чёрный» (дефолт 110): латте светлее.
   - `window_ms` — длина окна (дефолт 30000), под время варки твоей машины.
   ```
   curl "http://coffeecam.local/cupcfg?fill_delta=25&settle=6&milk_luma=110&window_ms=30000"
   ```

## Тест цикла верификации (эмуляция)

1. На ПК поднять слушатель вердиктов (узнать IP ПК: `ipconfig getifaddr en0`):
   ```
   python3 coffee/tools/verdict_listener.py            # 0.0.0.0:9000
   ```
2. Направить камеру на этот ПК:
   ```
   curl "http://coffeecam.local/cupcfg?host=<PC-IP>&port=9000"
   ```
3. Дёрнуть триггер и реально налить (или не налить) в стакан:
   ```
   curl "http://coffeecam.local/verify?drink=latte"          # async: вернёт started
   curl "http://coffeecam.local/verify?drink=espresso&wait=1" # block: вернёт вердикт JSON
   ```
   В слушателе появится строка `VERDICT #N OK/NOT_DISPENSED ...`. Сценарий
   «не налилось»: дёрни `/verify`, ничего не наливай → по таймауту прилетит
   `not_dispensed` (это и есть оспаривание списания).

> Без слушателя: `nc -lk 9000`. Вердикт также всегда лежит в
> `http://coffeecam.local/metrics` (`last_verdict`).
>
> ⚠️ `wait=1` держит HTTP-обработчик до конца окна — на это время порт 80 занят
> (другие запросы к камере ждут; стрим на порту 81 не затронут). Для живого
> тюнинга используй async-форму `/verify` + опрос `/metrics`.

## HTTP-эндпоинты

| Endpoint | Назначение |
|---|---|
| `/verify?drink=<...>` / `?milk=0\|1` / `?wait=1` | триггер верификации (эмуляция оплаты) |
| `/metrics` | живые метрики ROI + состояние + последний вердикт (для отладки) |
| `/cupcfg?...` | чтение/правка конфигурации (ROI, пороги, экспозиция, TCP), NVS |
| `/status` | полная диагностика: сенсор + верификатор + здоровье (uptime/heap/rssi/reset) |
| `/capture?roi=1` | кадр с рамкой ROI для прицеливания |
| `/stream`, `/`, `/control` | штатный стрим и веб-UI камеры |

`drink=`: `latte/cappuccino/flat white/mocha/macchiato` → ждём молоко;
`espresso/americano/black/ristretto/lungo` → без молока; иначе — только «налито/нет».

## Формат TCP-событий (NDJSON)

```json
{"type":"hello","dev":"coffeecam","ip":"192.168.1.50"}
{"type":"verdict","seq":7,"ts_ms":123456,"result":"not_dispensed","expected":"milk","dispensed":false,"milk":false,"fill_ms":0,"delta":3.1,"baseline_y":180.4,"final_y":181.0}
{"type":"status","rssi":-58,"uptime_s":3600,"heap":210000}
```

`result`: `ok` (налито и совпало с заказом) / `not_dispensed` (окно истекло, налива
нет → спорное списание) / `wrong_drink` (налито, но молочная ось не совпала).

## Надёжность / на что смотреть при отладке

- **Окно всегда завершается** вердиктом (нет «зависших» верификаций).
- Повторный `/verify` во время активного окна → **HTTP 409 busy** (не два окна).
- `reset_reason=9` в `/status` = **брауаут** (слабое питание): камера+WiFi дают
  броски тока, питай отдельным 5V ≥1А. `uptime_s` растёт = жив; обнулился = ребут.
- Дельта мала, хотя налил → ROI не на жидкости, или авто-экспозиция не
  зафиксирована (проверь `fixexp` в `/status`), или стакан прозрачный (видно
  насквозь — дельта слабее; подсветить фон/дно).
- **Латте в светлый стакан** даёт слабую дельту (крем по белому) → риск ложного
  `not_dispensed`. Проверь на реальном латте по `/metrics` и при нужде понизь
  `fill_delta`: слабая дельта тут роняет уже денежный вердикт, не только молоко.
- Тёмная поверхность кофе бликует от LED машины → блик в ROI скачет; сдвинь ROI
  или приподними `settle`.
- `milk` путается (пенка/crema) → это предел яркостной эвристики; см. этап 2
  ([`ml/README.md`](ml/README.md)) — CNN вставляется в `classify_milk()`.
