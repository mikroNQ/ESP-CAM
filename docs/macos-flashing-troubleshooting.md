# Прошивка ESP32-CAM на macOS: разбор проблем

Практическая шпаргалка по **реальным граблям** при заливке `CameraWebServer` на
«голый» AI-Thinker ESP32-CAM через USB-TTL переходник на macOS. Happy-path
описан в [`led-detector-guide.md`](led-detector-guide.md) (раздел 2) и в
`scripts/setup-esp-cam.sh`. Здесь — что делать, когда **не шьётся**.

> Контекст: на голом модуле ESP32-CAM нет USB и нет авто-сброса — прошивка идёт
> только через внешний USB-TTL (CP2102 / CH340), а в download-режим чип нужно
> вводить **вручную** (перемычка `IO0↔GND` + сброс). Большинство «непоняток»
> родом отсюда.

---

## TL;DR — если `arduino-cli upload` падает

1. **Освободи порт от зависших процессов** (причина №1, см. §1):
   ```bash
   pkill -9 -f "arduino-cli upload"; pkill -9 -f esptool
   lsof /dev/cu.usbserial-*           # должно быть пусто
   ```
2. **Один upload за раз.** Не запускай заливку из терминала и из скрипта
   одновременно — два esptool дерутся за порт и оба падают.
3. **Вход в download-режим** (голый модуль): перемычка `IO0↔GND` стоит →
   **чистый сброс** (кнопка `RST`, либо полное обесточивание). См. §2.
4. **Не выдёргивай USB-переходник из Mac**, чтобы «передёрнуть питание» — пропадёт
   COM-порт и esptool оборвётся (§3).

---

## 0. Какой у тебя переходник и драйвер

Имя порта и поведение зависят от чипа переходника:

```bash
ls /dev/cu.*                      # cu.usbserial-XXXX, cu.wchusbserial*, cu.SLAB_USBtoUART
# точный VID/PID и имя устройства:
ioreg -r -c IOSerialBSDClient -l | grep -iE "IOCalloutDevice"
system_profiler SPUSBDataType | grep -iE -A6 "serial|CP210|CH34"
```

| Чип | VID:PID | Имя порта (драйвер Apple) | Заметка |
|---|---|---|---|
| CP2102 (Silicon Labs) | `10C4:EA60` | `cu.usbserial-XXXX` | Встроенный `AppleUSBSLCOM`, обычно надёжен |
| CH340 (WCH) | `1A86:7523` | `cu.usbserial-XXXX` | Встроенный CH34x иногда капризен → родной драйвер WCH (`CH34xVCPDriver` в App Store) |
| CP2102 без серийника | — | `cu.usbserial-0001` | «0001» — типичный серийник дешёвых клонов |

> ⚠️ Имя `cu.usbserial-0001` само по себе **не** говорит, что это CH340 — это
> чаще CP2102-клон. Не гадай по имени, смотри VID/PID (`10C4:EA60` = CP2102).

**Драйвер обычно не виноват, если чтение работает.** Если в Serial виден бутлог
(`arduino-cli monitor` что-то печатает) — приёмный тракт и драйвер живы. Меняй
драйвер только когда доказано, что **передача** (Mac → переходник) не идёт (§5).

## 1. Самая частая засада: завис esptool и держит порт

Симптом: заливка стабильно падает на `Connecting......` → `No serial data
received`, **даже когда вход в download-режим сделан правильно**. Причина — в
системе **висит другой `esptool` / `arduino-cli upload`** (например, запущенный
раньше в другом окне терминала и застрявший в «Connecting»), и он **держит
порт**. Новые попытки дерутся с ним за тот же `/dev/cu.*`.

Проверка и лечение:
```bash
lsof /dev/cu.usbserial-0001         # покажет процесс, держащий порт
pgrep -fl "arduino-cli|esptool"     # все живые заливки
pkill -9 -f "arduino-cli upload"; pkill -9 -f esptool
```
После зачистки порт должен быть свободен (`lsof` пустой) — только тогда заливай.

> Этот же зависший процесс ломает и диагностику: тест петли (§5) покажет «эха
> нет», потому что байты съедает зависший монитор/esptool. Всегда проверяй
> `lsof` перед выводами.

---

## 2. Вход в download-режим (голый модуль, без авто-сброса)

Чип входит в режим прошивки, если **`IO0` притянут к `GND` в момент сброса**.
На голом модуле без авто-сброса это делается руками. Главное — **сброс должен
быть чистым** (полное передёргивание питания чипа), иначе условие не ловится.

Порядок:
1. Поставь перемычку **`IO0 ↔ GND`** (на правильном пине `IO0`; на AI-Thinker он
   рядом с `GND` на стороне `U0R/U0T`).
2. Сделай **чистый сброс** одним из способов (по надёжности):
   - **Кнопка `RST`/`EN` на плате** — лучший вариант: сбрасывает чип, не трогая
     питание и USB, порт не пропадает.
   - **Полное обесточивание** — выдерни **и USB, и питание**, через 3с верни. (Если
     питаешься от переходника — это и есть выдёргивание USB; тогда порт
     пересоздастся, см. §3 — делай это **до** запуска upload, не во время.)
3. Запусти `arduino-cli upload` — чип уже сидит в download-режиме и **ждёт
   бесконечно**, спешить не нужно.

**Почему не работает «дёрнуть только провод 5V»:** при подключённом 3.3В TX чип
**подпитывается через защитные диоды входа** и не выключается полностью —
сброса нет, в download-режим не входит. Поэтому дёргать 5V-провод бесполезно;
нужен `RST` или полное обесточивание.

> Косвенный признак входа в режим: после сброса **с перемычкой** Serial замолкает
> (ROM ждёт esptool), тогда как **без перемычки** сыпется бутлог. Но 0 байт сами
> по себе неоднозначны (может и сброса не было) — не полагайся только на это.

После заливки **сними перемычку `IO0↔GND`** — иначе firmware не стартует (чип
останется в download-режиме).

---

## 3. `could not open port ... No such file or directory`

Порт **пропал во время заливки**. Почти всегда — ты выдернул USB-переходник из
Mac, чтобы «передёрнуть питание». Делать так нельзя: переходник создаёт сам
COM-порт, и esptool теряет его на середине.

- Переходник **остаётся в Mac всё время** заливки.
- Сбрасывай чип кнопкой `RST` (порт не пропадает). Если приходится обесточивать
  полностью — делай это **до** старта upload, дай порту вернуться
  (`ls /dev/cu.*`), и только потом запускай заливку.

---

## 4. `No serial data received` — дерево решений

esptool отправляет sync, но чип не отвечает. Идём по порядку:

1. **Порт занят?** → §1 (`lsof`, `pkill`). Самая частая причина.
2. **Чип в download-режиме?** → §2. Перемычка `IO0↔GND` на правильном пине +
   чистый сброс (`RST`). «Дёрганье 5V-провода» сбрасывает ненадёжно.
3. **Передача Mac → чип работает?** Чтение (бутлог) ≠ запись. Проверь линию
   `адаптер TXD → камера U0R` и тест петли (§5). Линии должны быть крест-накрест:
   `TXD→U0R`, `RXD→U0T`.
4. **Драйвер** — только если §5 доказал, что передачи нет вообще (редко для
   CP2102).

---

## 5. Тест петли (loopback): передаёт ли Mac в переходник

Изолирует «читает, но не пишет». Сними оба сигнальных провода с камеры, на
переходнике **соедини `TXD` с `RXD`** напрямую и прогони (pyserial: `pip install
pyserial`, или системный python3 на macOS его обычно содержит):

```bash
python3 - <<'PY'
import serial, time
s = serial.Serial('/dev/cu.usbserial-0001', 115200, timeout=2)
s.dtr = True; s.rts = True; time.sleep(0.2); s.reset_input_buffer()
s.write(b'LOOP-TEST\r\n'); s.flush(); time.sleep(0.5)
print('echo:', s.read(200))
s.close()
PY
```
- Вернулось `LOOP-TEST` → **передача Mac/переходника исправна**; ищи проблему в
  проводе `TXD→U0R` или во входе в download (§2).
- Пусто → сначала **проверь `lsof` (§1)**: зависший процесс съедает эхо. Если порт
  чист, а эха нет — проверь, что перемычка реально на `TXD`↔`RXD` (не `DTR`/`GND`);
  и только потом думай на драйвер/переходник.

> Альтернатива без петли — посмотреть, **мигает ли светодиод `TX`** на переходнике
> во время непрерывной отправки. Мигает → передатчик жив.

---

## 6. После успешной заливки — проверка

1. Сними перемычку `IO0↔GND`, нажми `RST`.
2. Послушай Serial — должен быть **наш** бутлог (а не stock AT
   `Bin version(Wroom32)`):
   ```
   [boot] reset_reason=1
   *wm:AutoConnect ... STA IP Address: x.x.x.x   (или AP 'ESP32-CAM-Setup')
   Camera Ready! Use 'http://x.x.x.x'
   mDNS started: http://scanner.local/
   ```
   ```bash
   arduino-cli monitor -p /dev/cu.usbserial-0001 -c baudrate=115200 -q
   ```
3. Проверь по HTTP (когда камера в сети):
   ```bash
   curl -s http://<cam-ip>/status        # det_enabled, det_state, rssi, ...
   ```

Дальше — наведение ROI, экспозиция, TCP-endpoint и дашборд: см.
[`led-detector-guide.md`](led-detector-guide.md) разделы 4–8 и
[`QUICKSTART.md`](QUICKSTART.md).

## Сводка: симптом → причина

| Симптом | Вероятная причина | §  |
|---|---|---|
| `No serial data received`, вход в режим сделан верно | завис esptool/upload держит порт | §1 |
| `could not open port ... No such file or directory` | выдернул USB во время заливки | §3 |
| `No serial data received`, порт свободен | чип не в download-режиме (сброс/перемычка) | §2 |
| Бутлог читается, заливка не идёт | проверь передачу `TXD→U0R` / тест петли | §4–5 |
| После заливки firmware не стартует | не снята перемычка `IO0↔GND` | §2 |
| Сброс «дёрганьем 5V» не помогает | паразитное питание через TX → нужен `RST`/полное обесточивание | §2 |
